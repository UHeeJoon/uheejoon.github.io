사전예약 서비스 NOVA

판매가 열리면 10초 안에 5,000명이 몰리는 사전예약 서비스입니다. 사용자는 대기열에서 차례를 기다려 예약을 접수하고, 요청이 몰리면 느려지는 외부 예약 시스템 등록은 SQS를 거쳐 worker가 따로 처리합니다.

백엔드

예약과 보낼 메시지를 함께 저장해 유실 없이 처리한 외부 등록 비동기화외부가 멈춰도 접수 유지등록 유실과 중복 없음

찾은 문제

  • 요청이 몰리면 외부 예약 시스템이 느려짐
  • 접수가 외부 등록을 기다리는 구조라 접수도 함께 지연
  • 예약 저장과 외부 등록 요청 중 한쪽만 성공하면 예약과 외부 등록이 서로 맞지 않게 됨
검토한 안장점단점
외부 시스템 동기 호출구현이 단순외부가 느려지면 접수도 함께 느려짐
DB 저장 뒤 SQS 직접 발행구현이 단순커밋과 발행 사이에 죽으면 메시지 유실
Outbox + SQS (선택)발행하지 못한 행도 DB에 남아 재발행중복 발행이 생길 수 있어 받는 쪽 멱등 처리 필요

해결 과정

  • 접수 서버는 예약만 저장하고 바로 응답하며 외부 등록과 취소는 SQS에 넣어 별도 worker 서버가 처리
  • 예약과 Outbox 메시지를 한 트랜잭션으로 저장하고 커밋 직후 발행
  • 발행하지 못한 메시지는 Outbox Relay가 다시 발행
  • 같은 메시지가 두 번 갈 수 있어 예약 id를 멱등 키로 써서 중복 등록 방지
  • 처리하지 못한 메시지는 DLQ로 옮기고 한 건이라도 쌓이면 Slack 알림

결과

  • 외부가 느려지거나 멈춰도 접수는 그대로 처리되고 외부 등록만 늦어짐
  • 발행하지 못한 메시지는 Outbox에서 다시 발행하고 예약 id로 중복을 막아 외부 등록이 빠지거나 두 번 반영되지 않음
세마포어로 선착순 접수의 DB 커넥션 점유를 막은 동시 접수 제한접수 커넥션 10개 → 최대 5개나머지 절반은 조회 몫으로 보장

찾은 문제

  • 같은 상품의 접수는 선착순 순번 행 Lock에서 한 건씩 처리되는데 기다리는 동안에도 DB 커넥션을 쥔 채 대기
  • 대기열이 한 번에 100명 넘게 들여보내자 한 상품의 접수가 커넥션 10개를 모두 점유
  • 상관없는 조회 API는 커넥션을 2초 기다리다 503을 응답하고 Outbox Relay 발행도 지연

해결 과정

  • 줄을 DB 커넥션 대신 서버 메모리에 세우도록 접수 트랜잭션 앞에 세마포어 배치
  • 상품 하나당 동시에 2건(Lock을 쥔 1건과 다음 차례 1건)까지만 받고 접수 전체는 커넥션의 절반인 5건으로 제한
  • 한도에 막힌 접수는 커넥션 없이 기다리다 3초가 지나면 503과 1~3초 사이 무작위 Retry-After 응답
  • 같은 상품 12건을 동시에 접수하는 테스트로 2건만 트랜잭션에 들어가고 다른 상품 접수와 순번이 정상인지 확인

결과

  • 접수가 몰려도 커넥션 절반이 조회 몫으로 남아 커넥션을 2초 기다리다 503으로 실패하던 조회가 정상 응답
  • 한도에 막힌 접수는 커넥션 없이 기다려 한 상품에 접수가 몰려도 다른 상품의 접수와 조회가 함께 멈추지 않음
Lock 시점을 커밋 직전으로 옮긴 선착순 접수 개선p50 521ms → 48ms선착순 접수 응답 91% 단축

찾은 문제

  • 부하 시험에서 접수 서버를 늘려도 상품 하나의 접수는 초당 약 200건에서 정체
  • 느린 접수의 Tempo 트레이스에서 순번 행 SELECT FOR UPDATE 대기에 시간이 몰리고 DB CPU는 여유
  • Lock을 트랜잭션 맨 앞에서 걸어 다음 접수가 SQL 7개가 끝날 때까지 대기

해결 과정

  • 순번만 비운 채 나머지 행을 먼저 저장하고 커밋 직전에만 Lock을 걸어 Lock을 쥔 SQL을 7개에서 3개로 축소
  • 줄어든 대기만큼 상품 하나의 동시 접수 한도를 2건에서 4건으로 상향
  • 오픈 10초에 5,000명이 몰리는 상황을 k6로 변경 전 11회와 변경 후 4회 재현해 순번 중복과 빈 번호가 없는지 확인
접수 응답변경 전변경 후 (4회 평균)

외부가 느려지면 덜 보내도록 스스로 조절하는 동시 요청 한도고정 한도 → 2~16 자동 조절10초마다 외부 p95와 실패율로 판단

찾은 문제

  • 외부 예약 시스템은 평균 0.5초에 응답하고 약 5%가 실패함
  • 요청이 몰릴수록 외부 시스템의 부하가 커짐
  • worker가 SQS에서 꺼내는 대로 보내면 외부가 더 느려짐
  • 저장됐는지 알 수 없는 시간 초과 요청이 쌓임
  • 외부가 빠를 때와 느릴 때 알맞은 동시 요청 수가 달라 고정값으로 정할 수 없음

해결 과정

  • 외부로 동시에 보내는 요청 수를 세마포어로 제한해 외부가 느려지면 보내는 양도 자연스럽게 감소
  • 동시 요청 수는 8에서 시작해 worker 하나당 2~16 범위에서 조절
  • 등록은 한 자리를 남겨 두어 등록이 몰려도 취소는 항상 전송
  • SQS에서는 빈 자리만큼만 메시지를 가져옴
  • 보내지 못한 작업은 큐에 되돌려 잠시 뒤 재처리
  • 10초 Tumbling Window로 p95와 실패율을 모아 p95 1.5초 이상 또는 실패율 20% 이상이면 절반으로 감소
  • p95 1초 미만과 실패율 10% 미만을 지키면서 자리를 모두 쓰고 있을 때만 증가
  • TCP slow start처럼 값이 낮을 때는 두 배씩 늘리고 직전에 문제가 난 값의 절반부터는 1씩 증가

결과

  • 외부가 느려지면 동시 요청 수가 스스로 줄어 느려진 외부에 요청이 더 몰리는 악순환이 끊김
  • worker가 10초마다 알맞은 동시 요청 수로 조정해 외부 상태가 바뀌어도 사람이 한도 값을 고칠 필요가 없음
  • 외부가 회복되면 한도가 빠르게 다시 늘어 밀린 작업이 오래 쌓이지 않음
외부 실패를 원인별로 나눈 재시도와 SQS Polling 중단등록이 멈춰도 취소는 처리결과를 모르는 요청은 조회 후 재전송

찾은 문제

  • 외부 실패는 원인마다 다시 보내도 되는지가 달라 재시도 방식 하나로는 처리할 수 없음
실패 원인그대로 다시 보내면
외부 거절다시 보내도 같은 결과
우리 쪽 문제 (400번대)고칠 때까지 같은 결과
외부 장애 (연결 실패, 429, 503, connect timeout)잠시 뒤 성공할 수 있음
read timeout (3초 안에 응답 없음)등록됐는지 몰라 같은 예약이 두 번 등록될 위험

해결 과정

  • 외부 거절은 바로 DLQ로 보내고 우리 쪽 문제는 최대 30분 다시 시도한 뒤 DLQ로 보내 Slack으로 알림
  • 결과를 모르는 등록은 같은 멱등 키로 먼저 조회해 없을 때만 다시 전송
  • HTTP 클라이언트의 자동 재시도는 끔
  • 외부 거절이나 우리 쪽 문제가 1분에 5번이면 그 작업 종류(등록이나 취소)만 1분 동안 Polling 중단
  • 외부 장애가 최근 20건 중 절반 이상이면 Circuit Breaker를 열어 10초 동안 멈춤
  • Half-Open 동안에는 SQS에서 3건만 꺼내 보내 보고 2건 이상 성공하면 재개하고 아니면 두 배 더 멈춤 (최대 2분)
  • 1.5초 넘게 걸린 성공은 실패로 세지 않고 동시 요청 수 조절에만 반영
  • 멈춘 동안은 SQS에서 메시지를 꺼내지 않음

결과

  • 등록에서 문제가 이어져도 등록만 멈추고 취소는 계속 처리
  • 등록을 멈춘 동안 메시지가 DLQ로 가지 않고 SQS에 남아 원인을 고치면 다시 넣는 작업 없이 바로 처리
  • 느림은 동시 요청 수 조절이 맡고 실패는 Circuit Breaker가 맡아 외부가 느려지기만 할 때는 처리가 멈추지 않음
  • 결과를 모르는 요청은 조회한 뒤에만 다시 보내 외부에 두 번 등록되지 않음
대기열 입장 지연을 줄인 조회 간격 수정31초 → 3초대기열 입장 p95

찾은 문제

  • 대기열은 몰린 사용자를 줄 세워 접수 서버가 감당할 만큼만 1초마다 들여보내고 사용자는 서버가 알려 준 간격(차례가 가까우면 1초, 멀면 최대 30초)마다 차례를 확인
  • 10초 동안 5,000명이 들어오는 부하 시험에서 들여보내는 속도로 계산하면 10초 남짓이면 모두 입장해야 하는데 늦게 입장한 5%는 31초 넘게 걸림

원인

  • 몰리기 직전 한산할 때 계산해 둔 상품별 입장 속도가 0으로 남아 있었음
  • 대기 시간을 계산하지 못한 사용자는 가장 긴 30초 간격을 안내받아 차례가 지나고도 30초 뒤에야 확인

해결 과정

  • 입장 속도 값이 0이면 전체 입장 속도와 상품별 상한 중 작은 값으로 대기 시간을 계산
  • 같은 상품의 접수는 순번 행 Lock에 묶여 접수 서버를 늘려도 처리량이 그대로라 상품별 상한을 따로 둠

결과

  • 늦은 쪽 5%도 3초 안에 입장
  • 반복한 시험 모두에서 순번이 뒤로 밀린 사람이 없음

인프라

service.yml 하나로 서비스 배포 인프라가 준비되는 Terraform 폴더 구조인프라 담당 없이 서비스 추가Terraform 코드 수정 없이 service.yml PR 하나

설계 목표

  • 새 서비스를 배포할 때 Terraform 코드 수정 없이 서비스 폴더 추가만으로 인프라 준비
  • 모든 스택이 함께 쓰는 provider와 공통 값은 원본 한 곳 수정으로 전체 반영
  • 서비스마다 실제로 쓰는 권한과 네트워크만 허용

구조

  • 폴더를 서비스 선언, 공통 값, 자원별 스택으로 분리
  • 서비스마다 인프라는 service.yml, 앱은 application.yml, 비밀 값은 secrets.sops.yml로 application/ 아래에 선언
  • 스택마다 backend와 state를 따로 두어 한 스택의 변경이 다른 스택에 영향을 주지 않고 역할이 분명하게 나뉨
  • provider와 공통 값은 원본 하나를 링크로 공유하고 모든 자원에 제품, 환경, 관리 주체 태그를 자동 부여
  • 각 스택이 application/*/service.yml을 자동으로 찾아 새 서비스의 service.yml만 추가하면 ECR, IAM, 보안 그룹, ECS가 함께 생성
  • service.yml의 URL 경로와 태스크 수는 ALB와 ECS 설정으로, 호출 대상과 DB, 캐시는 보안 그룹 규칙으로, 큐는 IAM 권한으로 변환
  • 비밀 값은 apply 중에만 풀어 Secrets Manager에 넣고 state에는 남기지 않음
  • 오타 난 필드나 없는 서비스를 호출 대상으로 적은 선언은 서비스 이름과 원인을 보여 주고 plan에서 멈춤

결과

  • 새 서비스 배포와 설정 변경이 인프라 담당을 거치지 않고 Terraform 코드 수정 없이 서비스 폴더 PR 하나로 끝남
  • 공통 값과 provider를 바꿀 때 스택마다 고치다 하나를 빠뜨리는 일이 없음
  • 권한과 보안 그룹은 service.yml에 선언한 의존성만큼만 열리고 비밀 값은 Git과 state에 평문으로 남지 않음
PR을 거친 변경만 AWS에 적용되는 Atlantis 인프라 변경 절차모든 인프라 변경 PR로 추적plan과 apply가 PR 기록에 남음

설계 배경

  • 7명이 콘솔과 로컬에서 각자 바꾸면 코드에 남지 않아 누가 바꿨는지 모르고 잊힌 자원이 비용으로 남음
  • 같은 스택을 두 사람이 동시에 apply하면 state가 꼬임
  • 순서가 있는 스택은 거꾸로 적용하면 실패

운영 방식

  • PR 댓글로 plan과 apply를 실행하고 스택 잠금까지 기본 제공하는 Atlantis 선택
  • 팀원은 콘솔과 로컬 모두 읽기 전용 역할로 plan까지만 허용하고 비밀 값 스택의 복호화 권한은 제외
  • PR을 올리기 전 로컬 AWS 에뮬레이터 Floci에 스택을 apply해 적용 오류를 먼저 확인
  • VPC, 보안 그룹, DB, ECS 순으로 0~7단계를 atlantis.yaml에 적어 앞 단계가 실패하면 뒤 단계 중단
  • apply가 모든 스택에서 성공해야 PR이 자동 병합되어 main 브랜치가 실제 AWS와 같은 상태로 유지

결과

  • 모든 인프라 변경이 PR을 거쳐 적용되어 누가 언제 무엇을 바꿨는지 PR 이력으로 바로 추적
  • 콘솔에서 만든 채 잊힌 자원이 생기지 않고 main 브랜치와 실제 AWS가 일치
  • 같은 스택을 두 사람이 동시에 바꾸지 못하고 순서가 있는 스택은 정해진 순서대로만 적용
판매 오픈의 급증 트래픽과 큐 적체를 따라 늘어나는 ECS Fargate 확장 구조오픈 15분 전 사전 증설실패한 배포는 이전 버전으로 바로 복귀

설계 배경

  • 판매가 열리는 순간 대기열과 접수, 상품 조회에 트래픽이 몰리는데 CPU 기준 확장은 부하가 오른 뒤에야 반응
  • 외부 등록을 맡는 worker는 큐에 일이 밀려도 CPU가 낮아 CPU 기준으로는 늘어나지 않음
  • 새 버전이 망가져도 배포가 그대로 진행되면 판매 중에 사용자 요청이 실패

구조

  • HTTP 서비스는 CPU 기준 확장에 여러 대를 한 번에 늘리는 Step Scaling 정책을 더하고 축소는 5분 간격
  • worker는 큐 3개에 쌓인 메시지 합을 실행 태스크 수로 나눈 값을 지표로 써서 태스크당 50건 기준으로 조정
  • 사전예약 앱이 회차 일정을 보고 오픈 15분 전부터 예상 방문자 수만큼 대기열과 접수 서버의 최소 대수 상향
  • 상품 조회는 1대로는 몰리는 트래픽에 CPU가 포화돼 최소 2대로 늘리고 4대 상한에도 바로 닿아 최대 8대로 상향
  • ALB 뒤 서비스는 ECS Blue/Green으로 배포하고 5분 동안 이전 버전을 남겨 바로 복귀
  • 모든 서비스에 deployment circuit breaker를 켜 새 태스크가 계속 실패하면 이전 버전으로 자동 롤백

결과

  • 판매 오픈 첫 급증 트래픽은 증설을 기다리지 않고 미리 늘려 둔 서버로 처리
  • 큐가 처리량보다 많이 쌓이면 worker가 늘어나 외부 등록이 밀리지 않음
  • 배포 중에도 사용자는 한 버전의 응답만 받고 망가진 이미지는 사람 개입 없이 이전 버전으로 복귀
판매 오픈 순간의 급증 트래픽을 운영과 같은 경로로 재현하는 부하 시험 클러스터출시 전 병목 2건 발견고친 뒤 첫 1분 p95 30ms, 5xx 0%

설계 배경

  • 로컬 시험으로는 CloudFront, WAF, ALB와 자동 확장이 급증 트래픽을 어떻게 처리하는지 확인할 수 없음
  • 시험 트래픽이 운영 지표에 섞이거나 부하 발생기가 먼저 막히면 서비스 한계를 잴 수 없음

구조

  • 시험 리소스는 전용 ECS 클러스터에 모으고 평소에는 0대로 두어 시험할 때만 비용 발생
  • GitHub Actions 승인으로만 실행하고 실행 권한은 시험 클러스터로 한정
  • 오픈 10초 동안 5,000명이 들어오는 상황을 대기열부터 결제 시도까지 재현
  • k6 9대를 같은 시각에 시작하고 서버가 느려져도 보내는 양을 줄이지 않아 요청이 실제처럼 쌓이게 함
  • 시험 요청도 CloudFront, WAF, ALB를 그대로 지나고 k6는 NAT와 Spot 없이 띄워 대역폭 한계나 회수에 막히지 않게 함
  • WAF는 무작위로 만든 시험 헤더 값이 맞는 요청만 요청 수 제한에서 빼고 시험 지표는 운영 SLO 계산에서 제외
  • p95 0.5초와 5xx 0.1%를 기준으로 판정하고 계획한 부하를 못 보낸 시험은 판정 불가로 분리

시험으로 찾아 바꾼 설정

  • CPU 기준 확장은 새 태스크가 붙기까지 6~10분이 걸려 1분 지표 1~2번으로 바로 늘리는 Step Scaling을 추가
  • 헬스체크 간격을 15초에서 5초로 줄여 새 태스크가 요청을 받기까지 약 30초에서 약 10초로 단축
  • 대기열 태스크 한 대의 한계인 분당 약 6,000건을 재고 그 70%인 약 4,200건부터 증설하도록 설정

결과

  • 첫 시험은 첫 1분 p95 4.67초로 불합격했고 상품 조회 사양과 대기열 사전 증설을 고친 뒤 합격
  • 합격한 시험의 첫 1분은 초당 약 2,090건을 p95 30ms와 5xx 0%로 처리
서비스마다 필요한 리소스와 비밀 값만 받는 IAM과 Secrets Manager 구조고정 키 없이 운영비밀 값 평문 저장 없음

설계 배경

  • 7명이 AWS 계정 하나를 함께 써 누구든 쓰기 권한이 있으면 실수 하나가 계정 전체에 영향
  • 서비스가 같은 권한을 나눠 쓰면 하나가 뚫렸을 때 다른 서비스의 큐와 데이터까지 접근 가능
  • DB 비밀번호나 JWT 키 같은 비밀 값이 Git과 이미지, 태스크 정의에 평문으로 남으면 유출 경로가 늘어남

구조

  • 사람은 평소 읽기 전용 역할만 맡아 콘솔과 로컬 모두 조회와 plan까지만 허용
  • Atlantis 역할도 IAM은 nova-로 시작하는 프로젝트 자원만 다루고 자기 권한은 스스로 넓히지 못하게 막음
  • 서비스마다 task 역할을 따로 두고 service.yml에 적은 큐와 업로드 버킷만 허용
  • GitHub Actions는 OIDC로 main 브랜치에서만 배포 역할을 받고 태스크 정의는 Terraform만 바꾸게 함
  • 외부에서 받은 비밀 값만 KMS 키로 sops 암호화해 Git에 두고 복호화 역할은 Atlantis와 관리자로 한정
  • JWT 키, 여러 서비스가 함께 쓰는 비밀, 관리자 비밀번호는 apply 때 무작위로 만들어 Secrets Manager에 저장
  • 태스크 정의에는 값 대신 비밀 값의 위치만 적고 ECS가 태스크를 띄울 때 실행 역할로 읽어 환경변수로 주입
  • 실행 역할은 앱과 서비스 DB 계정 비밀만 읽고 DB 관리자, Grafana, Slack 같은 운영 비밀은 차단

결과

  • 서비스 하나가 뚫려도 피해가 그 서비스가 선언한 큐, 버킷, 비밀 값 안으로 한정
  • CI와 서비스는 실행할 때마다 임시 자격 증명을 받아 고정 키 없이 운영
  • 앱 비밀 값이 Git, state, 태스크 정의, 이미지 어디에도 평문으로 남지 않아 유출 경로 축소
목표 구조는 코드에 남기고 운영 비용만 73% 줄인 클라우드 비용 최적화월 비용 73% 절감약 890 → 240달러

찾은 문제

  • 6주 예산이 40만 원인데 Multi-AZ DB와 NAT Gateway, VPC 엔드포인트를 갖춘 목표 구조는 월 약 890달러라 예산을 넘음
  • Cost Explorer로 비용을 나눠 보니 서비스를 모두 띄운 뒤 Container Insights 지표 요금이 Fargate 다음으로 큰 비중
  • 그렇다고 설계를 낮추면 트래픽이 늘거나 예산이 생겼을 때 다시 만들어야 함

해결 과정

  • 처음 2주는 설계와 기획에 쓰고 인프라는 실제로 필요해진 뒤에 띄움
  • NAT 방식이나 Multi-AZ, 엔드포인트 같은 선택을 변수로 빼고 기본값만 싼 쪽으로 두어 목표 구조 코드는 그대로 유지
  • Container Insights는 끄기 전에 그 지표를 쓰던 경보와 worker 확장 기준부터 무료 지표로 이전
  • Container Insights 대신 서비스별 태스크 0개 경보와 ECS 이벤트 경보(배포 실패와 비정상 종료)로 장애 알림
  • NAT 인스턴스 교체 중 그 AZ의 외부 통신이 끊기는 점처럼 항목마다 감수할 점과 되돌리는 방법을 문서에 명시

결과

  • 한 달 약 890달러로 추정된 목표 구조를 실제 청구액 약 240달러로 73% 줄여 예산 안에서 운영
  • 줄인 항목은 대부분 변수 하나로 목표 구조로 되돌릴 수 있어 트래픽이 늘면 바로 복구
경보에서 원인까지 따라가 확장과 응답 지연을 개선한 모니터링증설 3분 지연 발견CloudWatch 지표 지연을 찾아 사전 증설로 대응

구축 이유

  • 503이 나도 CloudWatch와 로그 검색을 오가며 어느 서비스가 왜 실패했는지 직접 찾아야 함
  • 한 요청이 여러 서비스를 거치는데 서비스별 로그만으로는 요청의 흐름을 이어 볼 수 없음

구축 방식

  • OpenTelemetry Java 에이전트로 앱 코드 수정 없이 수집해 지표는 Mimir, 로그는 Loki, 트레이스는 Tempo, 프로파일은 Pyroscope에 저장
  • 트레이스는 오류와 느린 요청만 모두 남기고 나머지는 일부만 저장하는 대신 지표는 모든 요청으로 계산
  • 수집 게이트웨이를 관측 서버와 분리해 관측 서버를 재배포하는 동안 들어온 데이터도 잃지 않게 함
  • 판매 오픈 상황판 하나로 사용자 오류부터 그 서비스의 CPU 포화, Redis timeout, 증설 지연 같은 원인까지 추적
  • 경보는 서비스별 5xx와 SLO 예산 소진처럼 사용자가 겪는 증상을 기준으로만 발송

모니터링으로 개선한 것

  • 서비스별 CPU 사용량을 같은 시각으로 비교해 포화된 서비스를 찾고 태스크 사양과 최소 대수 상향
  • CloudWatch 1분 표준 지표가 약 3분 늦게 들어와 급증이 지나간 뒤에야 증설이 붙는 것을 찾아 오픈 전 사전 증설
  • 새 태스크가 CPU 부족으로 기동을 반복하다 deployment circuit breaker로 롤백되던 것을 찾아 CPU 할당 조정
  • 트레이스로 순번 행 Lock 대기를 찾아 Lock 시점을 커밋 직전으로 옮겨 응답 p50 521ms에서 48ms로 단축

결과

  • 503이 나도 CloudWatch와 로그를 오가지 않고 Grafana 한 화면에서 실패한 서비스와 원인까지 확인
  • 여러 서비스를 거친 요청을 트레이스 하나로 이어 보고 느려진 구간을 바로 찾음
  • 태스크 사양, 최소 대수, 증설 시점, DB 잠금 위치를 추측이 아닌 지표와 트레이스 근거로 조정
